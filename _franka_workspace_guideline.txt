Workspace Guide
This document explains the backend folder structure around:
~/franka_kinesthetic_teaching_GUI
~/franka_ws
~/franka_ws_jointfailsafe
~/FR3_visual_servo_examples
~/visp_install
It is not a replacement for the individual project READMEs. Those explain how to use a given repo. This guide explains how the folders fit together, which backend is active for which workflow, and why some changes require rebuilds while others do not.
Purpose Of Each Top-Level Folder
There are four main development areas in this setup.
~/franka_kinesthetic_teaching_GUI
This is the standalone kinesthetic-teaching GUI repo.
It contains:
the Tkinter GUI
teach/gravity launch logic
the joint recorder
the trajectory playback script
local documentation and logs
This repo is the source of truth for the GUI application itself.
~/franka_ws
This is the standard ROS 2 Franka workspace built from upstream-style resources.
It contains source packages under src/ such as:
franka_ros2
libfranka
visp
other related packages or wrappers that were part of the original setup
Think of this as the baseline or original robotics workspace on the machine.
~/franka_ws_jointfailsafe
This is the custom ROS 2 workspace used for the kinesthetic-teaching backend experiments.
It is the workspace that provides the current backend used by the kinesthetic-teaching GUI. It contains:
franka_ros2
libfranka
franka_joint_limit_failsafe
This workspace exists so controller experiments and backend changes do not have to be made directly in the original ~/franka_ws.
~/FR3_visual_servo_examples
This is the standalone visual-servo project.
It contains:
the actual visual-servo C++ code
its own CMakeLists.txt
its own run scripts
its own local build/ directory when compiled
This project is not built by colcon on each run. It uses its own direct CMake/Make build flow.
What A ROS 2 Workspace Is
A typical ROS 2 workspace built with colcon looks like this:
workspace/
  src/
  build/
  install/
  log/
 
Meaning:
src/
source code for ROS packages
this is the input to the workspace build
build/
intermediate build output
generated by colcon build
install/
installed packages, libraries, Python modules, launch files, and resources
this is what ROS uses when you source the workspace
log/
build logs and related diagnostics
Simple mental model:
src/ = source ingredients
build/ = build workspace
install/ = usable ROS environment
log/ = build records
What colcon build Does
colcon build is the standard build tool for a ROS 2 workspace.
When run in a workspace, it:
Scans src/ for ROS packages.
Resolves dependency order between those packages.
Builds packages in the correct order.
Writes intermediate build artifacts into build/.
Installs the built results into install/.
ROS does not usually run directly from src/ or build/. The usual runtime path is:
source install/setup.bash
 
That shell environment tells ROS where to find:
packages
launch files
executables
shared libraries
Python modules
plugin descriptions
What CMake Is In This Setup
CMake is a general build-system generator. It is not specific to ROS.
In this machine's setup:
colcon is used to build ROS workspaces like franka_ws and franka_ws_jointfailsafe
plain cmake plus make is used to build the standalone visual-servo project in FR3_visual_servo_examples
So:
kinesthetic-teaching backend: ROS workspace build with colcon
visual servo project: standalone C++ build with cmake and make
What ViSP Is
ViSP stands for Visual Servoing Platform.
It is a C++ library used for:
visual servoing
camera models
feature extraction and tracking utilities
robot interfaces
AprilTag-related vision tooling
image display and interaction tools
In this setup, the visual-servo project depends on ViSP.
Where ViSP Lives Here
There are two important ViSP-related paths:
source tree:
~/franka_ws/src/visp
installed ViSP used by the standalone visual-servo build:
~/visp_install
What we confirmed:
~/FR3_visual_servo_examples/CMakeLists.txt uses find_package(VISP REQUIRED)
~/FR3_visual_servo_examples/run_visual_servo_combined.sh configures CMake with:
-DVISP_DIR=$HOME/visp_install/lib/cmake/visp
that same script sets:
LD_LIBRARY_PATH=$HOME/visp_install/lib:...
So the current visual-servo build does use ViSP, but it uses the installed ViSP at ~/visp_install, not ~/franka_ws/src/visp directly during each run.
The likely role of ~/franka_ws/src/visp is:
source tree used to build or rebuild ViSP
reference code if ViSP itself must be patched
So:
~/visp_install = active installed ViSP dependency
~/franka_ws/src/visp = likely source-of-truth for rebuilding that dependency
The Two ROS Workspaces
This machine currently has two important Franka-related ROS workspaces:
~/franka_ws: standard workspace
This is the original or standard Franka workspace.
Use this description for it:
baseline workspace
built from standard resources and upstream-style packages
contains the original source layout used for the broader robot stack
It is useful as:
a reference workspace
a stable baseline
a place where source dependencies like visp may live
~/franka_ws_jointfailsafe: custom kinesthetic-teaching workspace
This is the custom workspace created for the kinesthetic-teaching backend.
Use this description for it:
experimental backend workspace
contains the custom joint-limit failsafe package
contains the modified Franka backend used by the kinesthetic-teaching GUI
It is useful as:
an isolated backend for controller experiments
the active ROS backend for teach/gravity mode and playback used by the GUI
This separation is intentional and valuable:
franka_ws stays closer to a standard baseline
franka_ws_jointfailsafe can evolve without directly disturbing that baseline
Current franka_ws_jointfailsafe/src Contents
What we confirmed is currently relevant in the custom workspace:
~/franka_ws_jointfailsafe/src/
  franka_joint_limit_failsafe
  franka_ros2
  libfranka
 
This source tree is sufficient for the custom backend workspace to build successfully.
Why src/ Matters
The src/ folder inside a ROS workspace is not just a backup copy. It is the actual source tree used by the build.
If you remove a required source repo from src/, then:
colcon build may fail
package discovery may become incomplete
the workspace may no longer represent a consistent backend
However, not every folder that happens to exist under src/ is necessarily part of the active runtime path.
That was an important lesson in this setup.
What We Confirmed About The Old GUI Package Copy
The custom workspace previously contained:
~/franka_ws_jointfailsafe/src/franka_kinesthetic_teaching_GUI
We confirmed all of the following:
it was an old independent copy
it was not being auto-updated from the standalone GUI repo
the current standalone GUI launch path was not using it
deleting it did not break the current kinesthetic-teaching setup
colcon build in ~/franka_ws_jointfailsafe still succeeded after removing it
So that package copy was redundant in the current architecture.
This is important because it shows:
a folder can exist under src/
yet still not be the thing that your current runtime path actually uses
Kinesthetic Teaching Architecture
The current kinesthetic-teaching setup is split between:
standalone GUI repo
custom ROS backend workspace
Standalone GUI side
The main GUI is launched from:
~/franka_kinesthetic_teaching_GUI
The current run_gui.sh effectively does:
source /opt/ros/humble/setup.bash
source ~/franka_ws_jointfailsafe/install/setup.bash
exec python3 franka_teach_run_gui_v2.py
 
That means:
GUI code comes from the standalone repo
ROS backend package resolution comes from the custom workspace
Backend side
The sourced custom workspace provides packages such as:
franka_bringup
franka_gripper
franka_description
franka_hardware
franka_fr3_moveit_config
your custom franka_joint_limit_failsafe package
Teach / gravity flow
When teach or gravity mode is started:
The standalone GUI launches its teach launch file from the standalone repo.
That launch file resolves ROS packages from the sourced franka_ws_jointfailsafe environment.
ROS starts the backend stack from that custom workspace.
The GUI then starts the recorder when appropriate.
So the architecture is:
orchestration and app logic = standalone GUI repo
robot backend packages = custom ROS workspace
Playback flow
When trajectory playback is started:
The standalone GUI starts the MoveIt/playback stack with ROS launch.
Package resolution again comes from ~/franka_ws_jointfailsafe/install/setup.bash.
Playback goes through the normal MoveIt and fr3_arm_controller path.
The standalone playback script publishes the replay trajectory.
Important distinction:
teach/gravity uses the custom soft-stop path
playback uses the MoveIt/controller path
Those are related flows, but not the exact same controller regime.
Visual Servo Architecture
The visual-servo setup is different from the kinesthetic-teaching setup.
There are two relevant pieces:
~/FR3_visual_servo_examples
This is the real visual-servo project.
It contains:
the actual C++ source code
the actual CMake build logic
the actual run script
We confirmed that:
run_visual_servo_combined.sh rebuilds the target on each run using cmake and make
the project links against ViSP from ~/visp_install
So this folder is the active visual-servo implementation.
~/franka_ws/src/chrps_visual_servo
This appeared to be a ROS wrapper package around the visual-servo project.
What we confirmed:
it mainly provided launch/script wrapping
it did not build the actual visual-servo C++ binary itself
your current visual-servo flow does not appear to require it
The practical reason is that the active path seems to launch the standalone visual-servo repo directly rather than using the ROS wrapper package as the main entrypoint.
So, for the current workflow:
FR3_visual_servo_examples matters directly
chrps_visual_servo looked redundant for the way the system is now being used
Why Visual Servo "Builds Every Time"
This was a source of confusion and is worth stating clearly.
The visual-servo run script does perform a build step every time it runs, but that build is:
not colcon build
not a ROS workspace rebuild
Instead it is:
local cmake
local make
in the standalone FR3_visual_servo_examples project
That is why visual servo feels different from the kinesthetic-teaching GUI flow.
Kinesthetic-teaching backend changes:
usually require rebuilding a ROS workspace with colcon
Visual-servo run script:
rebuilds its own standalone C++ target on launch
What "Sourcing A Workspace" Means
When you run:
source ~/franka_ws_jointfailsafe/install/setup.bash
 
you are telling the current shell to use that workspace's installed ROS environment.
That affects commands such as:
ros2 launch ...
ros2 run ...
Python ROS clients and nodes created from that shell
This is how the standalone kinesthetic-teaching GUI can remain outside the workspace but still use ROS packages provided by the workspace.
When Rebuilds Are Needed
You do not need to rebuild everything every time you use the robot.
Rebuild the custom ROS workspace when:
you change C++ code in ~/franka_ws_jointfailsafe/src/...
you change a package manifest
you change a package CMakeLists.txt
you change source that must be reinstalled into the ROS environment
Examples:
franka_joint_limit_failsafe
franka_ros2
libfranka
These changes usually require:
colcon build
 
or a package-limited colcon build --packages-select ...
Often no rebuild is needed when:
you edit standalone GUI Python scripts in ~/franka_kinesthetic_teaching_GUI
That is because the GUI is launched directly from source, not from an installed workspace copy.
Visual-servo rebuild behavior
For visual servo:
the standalone visual-servo script already runs its own CMake/Make build step
so source changes in FR3_visual_servo_examples are picked up by that local build path
This is a different mechanism from colcon.
Why A Change Sometimes Appears To Do Nothing
This is the most common source of confusion in multi-folder robotics setups.
You always need to ask:
which file am I editing?
which folder is actually being executed?
which workspace is currently sourced?
Examples:
editing ~/franka_kinesthetic_teaching_GUI/franka_teach_run_gui_v2.py affects the standalone GUI you actually launch
editing an old workspace copy of that GUI would not affect the standalone launch path
editing ~/franka_ws_jointfailsafe/src/franka_joint_limit_failsafe/... affects the custom backend, but only after rebuilding that workspace
editing ~/FR3_visual_servo_examples/... affects the standalone visual-servo project, which is rebuilt by its own run script

What To Keep In Mind For GitHub
This guide is mainly about structure, but it also supports the GitHub decision.
The main architectural takeaway is:
franka_ws is the standard baseline workspace
franka_ws_jointfailsafe is the custom kinesthetic-teaching backend workspace
FR3_visual_servo_examples is a separate standalone project with its own build flow
the standalone GUI is not itself the backend workspace
That means a future GitHub strategy should be deliberate about what is being published:
a backend workspace snapshot
a standalone GUI repo
a standalone visual-servo repo
or some combination with clear documentation
Short Version
The current machine setup works like this:
franka_ws is the standard Franka workspace and dependency baseline
franka_ws_jointfailsafe is the custom ROS backend used by the kinesthetic-teaching GUI
franka_kinesthetic_teaching_GUI is the standalone GUI app launched directly from source
FR3_visual_servo_examples is the standalone visual-servo project built with cmake and make
visp_install is the active installed ViSP dependency used by visual servo
If you change backend ROS code, you usually rebuild with colcon. If you change the standalone GUI, you usually rerun it directly. If you change visual-servo source, its own run script rebuilds the target with CMake/Make.
